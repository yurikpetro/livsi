# LIVSI — план реализации

Документ описывает стек, архитектуру, объём работ по этапам и оценку.
Основан на аудите (`01-audit.md`). Решения по оплате и доставке — в `03-payments-and-delivery.md`.

## 0. Рамка: чем должен быть сайт

Из брендбука следует, что первая покупка у обеих ЦА чаще происходит на Ozon/Wildberries. Значит сайт — это не «ещё одна витрина», а три роли одновременно:

1. **Бренд-платформа.** Носитель идеи «выбирай состояние», SEO-вход по небрендовым запросам, доверие (производство, документы, состав), контент.
2. **D2C-канал** с маржой выше маркетплейсовой: наборы, лимитки, миниатюры, подарок к заказу, «собери ритуал» — то, что на маркетплейсе продавать неудобно.
3. **B2B-канал для мастеров (PRO):** прайс, быстрый повторный заказ, документы для юрлиц.

Три следствия для архитектуры, которые дешевле заложить сразу:
- **Один источник правды по остаткам и ценам.** Сайт торгует тем же складом, что WB/Ozon. Либо учётная система (1С / МойСклад) — мастер, а сайт — потребитель, либо наоборот. Решить до старта, иначе овербукинг и разъезд цен.
- **Мультипрайс с первого дня в модели данных** (B2C-розница + PRO-опт по уровням), даже если B2B-интерфейс выйдет во второй волне.
- **Провайдеры оплаты и доставки — за интерфейсами.** Сегодня СБП + Ozon, завтра карты + СДЭК. Смена провайдера не должна означать переписывание чекаута.

## 1. Стек

Рекомендация с обоснованием: дизайн кастомный и «брендовый» (крупная типографика, паттерны, нестандартные сетки) — типовая CMS будет мешать больше, чем помогать; проект уже открыт в PhpStorm, то есть основная компетенция — PHP.

| Слой | Выбор | Почему |
|---|---|---|
| Язык / фреймворк | PHP 8.3+, **Laravel 12** | Скорость разработки, очереди/шедулер/вебхуки из коробки, зрелые пакеты под платежи и медиа |
| БД | **PostgreSQL 16** | JSONB под атрибуты товара, нормальный full-text, оконные функции для отчётов |
| Кэш / очереди | **Redis** + Laravel Horizon | Вебхуки оплаты, синхронизация остатков, письма — только через очереди |
| Админка | **Filament 3** | Готовые CRUD, роли, медиа. Экономит 80–120 ч против самописной |
| Фронт | **Blade + Livewire 3 + Alpine.js**, Vite, **Tailwind CSS 4** | SSR по умолчанию (важно для SEO), фасеты и корзина без отдельного SPA. Альтернатива — Inertia + Vue 3, если захотим «приложение»-чекаут |
| Поиск | PG full-text на MVP → **Meilisearch** при >300 SKU | Опечатки, синонимы («парафин»/«paraffin»), фасеты |
| Медиа | `spatie/laravel-medialibrary` + WebP/AVIF, S3-совместимое хранилище (Selectel / VK Cloud / Yandex Object Storage) + CDN РФ | Из аудита: исходники по 5 МБ, нужен пайплайн |
| Инфраструктура | Docker (dev), VPS/выделенный **в РФ**, nginx, GitHub Actions/Deployer, staging | 152-ФЗ: персональные данные россиян — на серверах в РФ |
| Мониторинг | Sentry/GlitchTip, healthcheck, алерты в Telegram | Отвалившийся вебхук оплаты нужно замечать в минутах, а не в днях |
| Тесты | **Pest** | Обязательное покрытие: корзина, промокоды/подарок, расчёт доставки, вебхуки оплаты, идемпотентность |

### Альтернативы стеку — если заказчик захочет иначе

| Вариант | Плюсы | Минусы |
|---|---|---|
| **1С-Битрикс** («Малый бизнес») | Готовые модули оплаты (ЮKassa/СБП), обмен с 1С «из коробки», легко найти подрядчика на поддержку, привычно бухгалтерии | Лицензия + продление; кастомный дизайн реализуется «через сопротивление» платформы; тяжёлое ядро, медленный DX; переделка макета под компоненты — отдельные часы |
| **InSales / AdvantShop** (SaaS) | Запуск в недели, 54-ФЗ, СБП и доставки уже интегрированы, поддержка на стороне платформы | Абонплата навсегда; дизайн — компромисс с шаблоном (макет придётся упрощать); vendor lock-in; ограниченная логика B2B-прайсов |
| **WooCommerce / OpenCart** | Дёшево, много российских модулей оплаты и доставки | Производительность и безопасность требуют постоянного внимания; качество модулей разное; кастомный дизайн + сложные фасеты быстро превращаются в борьбу |
| **Headless (Nuxt/Next + Medusa/Strapi)** | Максимальная гибкость фронта, отличный Core Web Vitals | Дороже на 30–50 %; нет российских интеграций из коробки — всё писать; требует JS-компетенции в поддержке |

Вывод: **Laravel + Filament** — оптимум по «кастомный дизайн × российские интеграции × стоимость поддержки». Если приоритет — «запустить максимально быстро и дешево, дизайном можно поступиться», то InSales.

## 2. Архитектура

```
[ Клиент (Blade/Livewire) ]
          │
   [ Laravel app ]───[ PostgreSQL ]
     │  │  │  │
     │  │  │  └──[ Redis: cache, queues, sessions ]
     │  │  │
     │  │  └──[ Filament admin ]
     │  │
     │  └──[ Domain services ]
     │        ├── Catalog        (товары, варианты, фасеты)
     │        ├── Pricing        (B2C / PRO-прайсы, промокоды, подарок)
     │        ├── Cart & Checkout
     │        ├── PaymentGatewayInterface  ──> СБП-провайдер (заменяемый)
     │        ├── ReceiptProviderInterface ──> 54-ФЗ / ОФД
     │        ├── DeliveryProviderInterface──> Ozon (+ СДЭК/Почта позже)
     │        └── InventorySync           ──> 1С / МойСклад
     │
     └──[ Webhooks in: оплата, доставка, ОФД ] (идемпотентно, с логом)
```

**Ключевые инженерные правила проекта**

1. **Источник правды по оплате — только вебхук**, не redirect с фронта. Redirect — лишь UX.
2. **Идемпотентность обязательна**: `payments.idempotency_key` на исходящих запросах, `webhook_events.external_id UNIQUE` на входящих. СБП/ОФД/доставка ретраят события.
3. **Резерв склада на время оплаты** с TTL, равным времени жизни QR (обычно 5–20 мин), + фоновая задача снятия резерва.
4. **Цена и состав заказа фиксируются в `order_items`** на момент оформления. Изменение прайса не должно менять историю.
5. **Все внешние вызовы — в очередях с ретраями и бэкоффом**, синхронно только то, что нужно пользователю сейчас (расчёт доставки, создание платежа).
6. **Логи интеграций хранить с телом запроса/ответа** (с маскированием ПД) — без этого споры с эквайером и Ozon неразрешимы.

### Модель данных (ядро)

- `product_lines` — fresh/sweet/warm/base/pro: цвета, паттерн, тип (`b2c`/`pro`), описание
- `states` — «состояния» для навигации. **Требует уточнения:** состояние == линейка (как в макете) или отдельная ось (тогда many-to-many)
- `categories` — тип продукта: пенка, скраб, крем-парафин, гель, спрей…
- `attributes` / `attribute_values` — аромат, назначение (лицо/тело/руки/ноги), тип кожи, «главные действия»
- `products` — наименование, slug, `line_id`, `category_id`, аромат/ключевые компоненты, главные действия, состав INCI, действующие вещества (PRO), применение, срок годности, SEO-поля, документы
- `product_variants` — объём/вес, SKU, EAN-13, **вес и Д×Ш×В** (без них доставка не считается), цена, цена «до», статус
- `bundles` / `bundle_items` — наборы и подарочные боксы (ЦА2: «готовое решение»)
- `price_lists`, `prices` — B2C-розница + PRO-уровни (base/silver/gold)
- `stocks`, `stock_reservations` — остатки и резервы
- `carts`, `cart_items` — гостевые (по cookie) и привязанные к пользователю
- `orders`, `order_items`, `order_status_history`
- `payments`, `refunds`, `receipts` (54-ФЗ), `webhook_events`
- `shipments`, `shipment_events`, `pickup_points` (кэш ПВЗ/постаматов с координатами)
- `promocodes`, `promotion_rules` (бесплатная доставка от N ₽, подарок от N ₽)
- `customers`, `addresses`, `wishlists`, `reviews`, `review_media`
- `companies` — для B2B: ИНН/КПП, реквизиты, `price_list_id`, менеджер
- `pages`, `posts`, `subscribers`, `ugc_items`
- `sync_logs` — обмен с учётной системой

**Обязательные согласования по дизайн-системе** (иначе вёрстка будет переделываться):
1. межстрочное для body — 100 % (брендбук) или 1,35–1,5 (веб-норма);
2. `#000000/#FFFFFF` (брендбук) или `#0A0A0A/#FFFDF8` (макет);
3. tracking H1/H2 — по брендбуку (−3 %/−2 %) или по макету (−5,5 %/−4,5 %);
4. цвет ошибки/предупреждения — в брендбуке его нет, а формам он нужен;
5. минимальный размер логотипа в px (в брендбуке нормируется в мм для печати; в макете — 128×56 px);
6. фавикон и иконки приложения — из эмблемы-«клевера» (стр. 26–27, 34).

## 4. Объём работ по этапам

### Этап 0. Дискавери и ТЗ
Заполнение опросника (`04-questions-for-client.md`), фиксация: юрлицо и налоговый режим, банк/эквайер, домен, учётная система, номенклатура и прайс, наличие договора с Ozon. Результат — подписанное ТЗ и матрица «MVP / v2».

### Этап 1. Достройка дизайна (блокирующий)
UI-kit по брендбуку (кнопки, поля, чипсы, карточки, таблицы, тосты, модалки, состояния) + экраны, которых нет: каталог, карточка, корзина, чекаут (3 шага), статусы оплаты, ЛК (4–5 экранов), авторизация, поиск/пусто/404, статические страницы, PRO-раздел, cookie-баннер. Всё — desktop + mobile, ключевые — tablet.

### Этап 2. Каркас
Репозиторий, окружения (local/staging/prod), CI/CD, Docker, базовый layout, подключение Geist, токены/Tailwind-пресет, SVG-спрайт иконок, image-пайплайн, вёрстка главной 1:1 с макета + доработка адаптива (добавить tablet-брейкпоинт), доступность базового уровня.

### Этап 3. Каталог
Импорт номенклатуры (CSV/Excel → варианты, атрибуты, фото), листинг с фасетами (состояние/линейка, тип продукта, аромат, назначение, объём, цена, наличие), сортировки, пагинация/«показать ещё», карточка товара (галерея, выбор объёма, состав, применение, документы, «с этим покупают»), наборы, лимитки, избранное, поиск, SEO (ЧПУ, meta, Schema.org Product/Offer, sitemap, OG), страницы линеек как лендинги.

### Этап 4. Корзина и чекаут
Гостевая корзина, авторизация (по коду на телефон/e-mail — уточнить), мини-корзина, промокоды, правила «бесплатная доставка от N ₽» и «подарок от N ₽», чекаут: контакты → способ получения (ПВЗ на карте / курьер / самовывоз) → оплата, валидация, согласия (оферта + 152-ФЗ), создание заказа, письма/СМС.

### Этап 5. Оплата (СБП)
Интеграция выбранного провайдера: создание платежа, QR + deeplink в банковское приложение, страница ожидания с поллингом, вебхук с проверкой подписи и идемпотентностью, статусная модель, TTL и авто-отмена, полный и частичный возврат из админки, чеки 54-ФЗ (приход + возврат), тестовый контур, юнит/фича-тесты на все ветки.

### Этап 6. Доставка (Ozon)
Справочник ПВЗ/постаматов + виджет выбора на карте, расчёт стоимости и срока по габаритам/весу, создание отправления, печать этикеток/ШК, реестр отгрузки, трекинг и статусы в ЛК и письмах, обработка возвратов, фолбэк на «ручной режим» при недоступности API.

### Этап 7. ЛК, контент, маркетинг
ЛК: заказы, статусы, трекинг, повтор заказа, избранное, адреса, подписки. Контент-страницы и блог. Подписка на рассылку (double opt-in) + брошенная корзина. Аналитика: Яндекс.Метрика + e-commerce, цели, VK/MyTarget пиксели, фиды (Яндекс Маркет / VK). Отзывы с модерацией. UGC-галерея.

### Этап 8. Приёмка и запуск
Юр. документы на сайте (оферта, политика, согласие, условия возврата), уведомление РКН об обработке ПД, cookie-баннер, нагрузочное тестирование, Core Web Vitals, чеклист OWASP, бэкапы и восстановление, инструкции для контент-менеджера и менеджера заказов, обучение, перенос на прод, мониторинг первых дней.

### Этап 9 (v2). Развитие
PRO/B2B-кабинет (прайсы по уровням, минимальный заказ и кратность, счёт на оплату, УПД, отсрочка, персональный менеджер), интеграция с 1С/МойСклад (двусторонняя), программа лояльности/бонусы, «собери свой ритуал», подписка на регулярную доставку, расширение доставок (СДЭК/Почта), карты и BNPL, A/B-тесты, Telegram-бот для мастеров.

## 5. Оценка

Оценка в человеко-часах разработки; дизайн и менеджмент — отдельно. Диапазон отражает неопределённость до ответов заказчика.

| Этап | Разработка, ч | Дизайн, ч | Комментарий |
|---|---|---|---|
| 0. Дискавери и ТЗ | 16–24 | 4–8 | Зависит от скорости ответов заказчика |
| 1. Достройка дизайна | — | 80–140 | Блокирует этапы 3–7 |
| 2. Каркас + главная | 60–80 | 8–16 | Вкл. шрифты, токены, image-пайплайн, tablet |
| 3. Каталог | 90–130 | — | Растёт с числом атрибутов и SKU |
| 4. Корзина и чекаут | 70–100 | — | Промо-правила — самая коварная часть |
| 5. Оплата СБП + 54-ФЗ | 50–70 | — | +20–30 ч, если добавлять карты и BNPL |
| 6. Доставка Ozon | 45–70 | — | Сильно зависит от качества API Ozon |
| 7. ЛК, контент, маркетинг | 60–90 | — | Без блога-конструктора |
| 8. Приёмка и запуск | 30–45 | — | Вкл. правки по итогам тестирования |
| **MVP итого** | **420–610** | **92–164** | |
| 9. B2B/PRO-кабинет | 120–180 | 24–40 | Обычно v2 |
| 9. Интеграция 1С/МойСклад | 60–120 | — | Двусторонняя, с логами и разбором конфликтов |

Плюс менеджмент и QA: **+20–25 %** к разработке.

**Календарный срок MVP:** 10–14 недель при одном фулстек-разработчике и дизайнере на part-time, при условии что заказчик отвечает в течение 2 рабочих дней и контент (фото, тексты, прайс) приходит к началу этапа 3. Каждая неделя задержки контента = неделя сдвига запуска.

**Что сокращает срок**, если нужно быстрее:
- вынести в v2: B2B, отзывы, блог, UGC, «собери ритуал», избранное;
- на старте — одна доставка (Ozon ПВЗ) и один способ оплаты (СБП);
- каталог до 40 SKU.

Это даёт «витрина + каталог + чекаут + СБП + Ozon» примерно за **320–420 ч и 8–11 недель** — сценарий А в [`05-platform-choice.md`](05-platform-choice.md).

> Уточнение от 12.08.2026: отказаться от вариативности товара («один товар = один SKU») нельзя — реальные товары варьируются и по объёму, и по аромату. См. раздел 7 и `01-audit.md`, п. 7.3.

## 7. Уточнения после первых ответов заказчика (12.08.2026)

Получена часть ответов по опроснику (протокол — в `04-questions-for-client.md`, раздел 13). Ниже то, что меняется в плане. Этот раздел имеет приоритет над более ранними разделами документа там, где они расходятся.

### 7.1 Что уходит из объёма

Отзывы · блог · лимитированные коллекции · «сообщить о поступлении» · подписка на регулярную доставку · BNPL · подарочные сертификаты · миниатюры и пробники · товарные фиды для рекламы · обучение и инструкции для контент-менеджера.

UGC упрощается до подборки картинок, загружаемых в админке (без сбора прав и модерации).

### 7.2 Что добавляется в объём

**Интеграция с МойСклад** — переезжает из v2 в MVP. Причина: 90 % оборота идёт через WB и Ozon с того же склада, товар уже учитывается в МойСкладе. Без синхронизации сайт будет продавать то, чего нет.

Архитектура обмена (МойСклад — мастер, сайт — потребитель):

| Направление | Что передаём | Как | Частота |
|---|---|---|---|
| МойСклад → сайт | остатки, цены | вебхуки МойСклада + сверочный полный прогон | вебхук сразу, сверка раз в 15–30 мин |
| МойСклад → сайт | номенклатура: товары, варианты, штрихкоды, вес/габариты | первичный импорт + инкрементальный | по расписанию / вручную из админки |
| Сайт → МойСклад | заказ покупателя после подтверждения оплаты | API, идемпотентно | по факту оплаты |

Технические решения по обмену:
- **Резерв на время оплаты ведём локально**, а заказ покупателя в МойСкладе создаём уже после подтверждения оплаты. В МойСкладе резерв технически возможен через заказ покупателя, но заводить его на 15 минут ожидания оплаты QR — лишний мусор в учёте и риск рассинхрона. Доступное к продаже = остаток из МойСклада − локальные активные резервы.
- **У API МойСклада есть лимиты частоты запросов** — вся синхронизация только через очереди, пачками, с бэкоффом.
- **Вес и габариты берём из МойСклада**, но их там почти наверняка нет — нужно проверить и, если пусто, заполнить. Без них не считается доставка. Это отдельная задача заказчику.
- Обязателен **лог обмена и отчёт о расхождениях** — иначе разбирать инциденты с остатками невозможно.

Плюс к объёму: **вариативность товара по двум осям** (объём × аромат) вместо простого поля «объём»; **механика подарочного бокса** от суммы заказа с учётом склада и корректным отражением в чеке; **настройки промо-порогов в админке**.

### 7.3 Порог бесплатной доставки: не env, а админка

Просьба была «менять через env». Предлагаю иначе: **настройка в админке, а значение из env — только как значение по умолчанию при первом деплое**.

Причина: правка `.env` требует доступа к серверу и перезапуска приложения, то есть менять порог будет разработчик. А автономность заказчика в таких вещах — ровно то требование, из которого выросло решение делать своё решение вместо конструктора. Порог, подарок, тексты акции в топбаре — это маркетинговые параметры, их место в интерфейсе.

Дополнительно: раз доставку при бесплатной оплачивает продавец, в заказе нужно **отдельное поле «фактическая стоимость доставки»** (то, что выставил перевозчик) — иначе реальная маржа заказа непрозрачна. Плюс отчёт «сколько потратили на бесплатную доставку за период».

Пороги 3 000 / 5 000 ₽ из макета не сходятся с фактическим средним чеком — обоснование и ориентиры в `01-audit.md`, п. 7.5.

### 7.4 Инфраструктура: Timeweb

Подходит, но нужен **Timeweb Cloud (VPS/облачный сервер), а не виртуальный хостинг** — проекту требуются PostgreSQL, Redis, воркеры очередей под supervisor и планировщик. На shared-хостинге это не живёт.

Ориентир для старта: 2–4 vCPU, 4–8 ГБ RAM, 60–80 ГБ NVMe. Медиа — в S3-совместимое хранилище Timeweb. Обязательно: бэкапы БД (ежедневно, хранение 14–30 дней) и медиа, отдельный staging-контур, сертификат Let's Encrypt.

### 7.5 Юридические тексты — шаблонные, юриста нет

Принято. Риск: шаблонная оферта почти всегда расходится с реальными процессами, а спрос идёт по тому, что написано на сайте. Минимум, что нужно вычитать и привести в соответствие с фактом:

- сроки доставки и сроки передачи заказа в службу доставки;
- условия и сроки возврата денег;
- порядок отказа от товара при дистанционной продаже: **7 дней после получения** (и почему именно так — `06-scope-v2.md`, § 2.2), обязательная памятка о возврате в посылке, условия удержания расходов на обратную доставку;
- порядок отмены заказа покупателем и продавцом;
- реквизиты продавца.

Ответственность за содержание документов — на заказчике, это стоит зафиксировать письменно.

### 7.6 SEO без блога и без отзывов

Из инструментов остаются: страницы линеек и категорий как посадочные, страницы фасетов с отдельными адресами, микроразметка товара, sitemap, корректные title/description, скорость. Ставку на органику при таком наборе делать нельзя — основным каналом остаётся перевод трафика с маркетплейсов и соцсетей.

Отдельно: 39 000 заказов и рейтинг 4.9 на Ozon — накопленный актив, который на сайт не переносится. Отзывы решено не делать, но дешёвый компромисс есть: **блок «Что о нас пишут» с подборкой отзывов, которую заказчик наполняет в админке вручную** (те же 8–12 ч, что и UGC-подборка). Без формы, без модерации, без интеграций. Рекомендую не отказываться от этого совсем — при цене ниже маркетплейсной доверие придётся чем-то подкреплять.

### 7.7 Поддержки после запуска не будет

Принято, но зона риска очевидная: если отвалится вебхук платёжного провайдера или обмен с МойСкладом, магазин будет молча терять заказы. Минимум, который стоит оставить даже без договора на поддержку:

- мониторинг и алерты в Telegram: нет вебхуков оплаты дольше N минут, ошибки обмена с МойСкладом, 5xx, место на диске, просроченные задачи очереди;
- сверочный отчёт «заказы vs платежи vs чеки» с ежедневной отправкой на почту;
- договорённость о порядке действий при инциденте, даже без регулярных часов.
