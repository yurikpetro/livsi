# LIVSI — оплата и доставка: варианты, плюсы и минусы, рекомендация

Исходная вводная от заказчика: **оплата предварительно только через СБП**, **доставка предварительно через Ozon Доставку**.
Ниже — разбор этих решений, альтернативы и то, что нужно спроектировать в любом случае.

> Все тарифы и названия продуктов — ориентиры на середину 2026 года. Они меняются, финальные цифры берём из договоров с банком и Ozon. Ни одна интеграционная деталь ниже не является заменой официальной документации провайдера.

## Часть 1. Оплата

### 1.1 Что важно понять про СБП до выбора

СБП (Система быстрых платежей НСПК) в сценарии интернет-магазина — это C2B-платёж по QR-коду или платёжной ссылке. Технически это выглядит так: сайт создаёт платёж → получает QR/deeplink → покупатель подтверждает в приложении своего банка → магазину приходит вебхук. Деньги зачисляются на расчётный счёт практически мгновенно.

Отдельно: в 2025–2026 идёт переход на **универсальный QR-код НСПК**. Сроки и порядок для конкретного банка нужно уточнить у эквайера — это может повлиять на способ отображения QR на сайте.

### 1.2 Варианты приёма оплаты

#### A. СБП через платёжного агрегатора (ЮKassa, Т-Касса, Робокасса, PayKeeper, CloudPayments, эквайринг Альфы/ПСБ/Сбера)

**Плюсы**
- Одна интеграция — потом карты, СберPay/Т-Pay/Mir Pay, BNPL включаются без переписывания кода.
- Фискализация 54-ФЗ часто встроена (ЮKassa, Т-Касса) — отдельная касса не нужна.
- Готовые SDK/пакеты для PHP, песочница, понятная документация, техподдержка.
- Возвраты (полные и частичные) через API, возвратный чек — автоматически.
- Личный кабинет с реестрами — бухгалтерии проще сверять.

**Минусы**
- Комиссия чуть выше, чем при прямом подключении СБП: агрегатор берёт свою маржу поверх тарифа НСПК.
- Деньги приходят по расписанию расчётов агрегатора (обычно на следующий рабочий день), а не мгновенно.
- Зависимость от третьей стороны: их авария = наш неработающий чекаут.

**Комиссия-ориентир:** СБП 0,4–0,7 % (розница обычно ближе к 0,7 %), карты 1,5–3,5 %.

#### B. СБП напрямую у банка-эквайера (C2B QR/ссылка от Т-Банка, Сбера, Альфы, Точки, Модульбанка)

**Плюсы**
- Самая низкая комиссия — тариф НСПК почти без наценки.
- Мгновенное зачисление на расчётный счёт в том же банке.
- Меньше посредников — меньше точек отказа.

**Минусы**
- **Только СБП.** Карты — отдельный договор интернет-эквайринга, отдельная интеграция.
- **Фискализация 54-ФЗ на нас**: нужна облачная касса (АТОЛ Онлайн, Модулькасса, Бизнес.Ру и т. п.) и отдельная интеграция — это +20–40 ч работы и ещё одна абонплата.
- API у банков разного качества; песочница есть не у всех.
- Смена банка = переписывание интеграции.

#### C. Полный интернет-эквайринг (карты + СБП + Pay-кнопки + BNPL)

**Плюсы**
- Максимальная конверсия: покупатель платит привычным способом.
- Сохранённые карты, оплата «в один клик», повторные и регулярные платежи (важно, если появится подписка на пополнение ухода).
- BNPL (Долями, Яндекс Сплит, Подели) поднимает средний чек — актуально для наборов и подарочных боксов.

**Минусы**
- Комиссия по картам 1,5–3,5 % против 0,7 % по СБП — на среднем чеке 1 500–3 000 ₽ это заметно.
- Больше сущностей: холд/списание, чарджбэки, антифрод, 3-D Secure.
- Дольше внедрение и приёмка.
- PCI DSS: сами карты не храним (используем платёжную страницу провайдера), но требования всё равно нужно соблюдать.

#### D. Ручные ссылки/QR из банковского приложения (нулевой MVP)

**Плюсы**: работает завтра, без интеграции и без затрат.
**Минусы**: нет автоматического подтверждения оплаты — менеджер сверяет вручную; нет автоматических чеков; невозможна аналитика конверсии; заказы теряются; не масштабируется. Только как временная заглушка на 2–4 недели.

#### E. Оплата при получении (наложенный платёж через службу доставки)

**Плюсы**: снимает барьер недоверия к незнакомому бренду; для ЦА1 (мастера) удобно.
**Минусы**: невыкупы 10–30 % и оплата обратной логистики за наш счёт; деньги приходят с задержкой и с комиссией перевозчика; замороженный товар в пути; сложнее фискализация (чек в момент получения). **Нужно отдельно подтвердить у Ozon, поддерживается ли наложенный платёж для сторонних магазинов.**

#### F. Безналичный расчёт по счёту (для B2B/PRO)

Обязателен, если появится PRO-канал: юрлица и часть самозанятых платят по счёту, а не картой. Плюсы: нулевая комиссия, крупные чеки. Минусы: ручной процесс (счёт → ожидание → сверка → отгрузка), нужна генерация счёта и УПД, контроль дебиторки. Реализуется как отдельный «способ оплаты» без онлайн-подтверждения.

#### G. BNPL (Долями / Яндекс Сплит / Подели)

Плюсы: +средний чек, хорошо работает на наборах 3 000–7 000 ₽. Минусы: комиссия выше карточной (обычно), дополнительный договор, свои правила возвратов. Кандидат в v2.

### 1.3 Честная оценка режима «только СБП»

**За СБП как основной способ:**
- Комиссия в 3–4 раза ниже карточной. На обороте 1 млн ₽/мес экономия ≈ 20–25 тыс. ₽.
- Нет чарджбэков и почти нет фрода.
- Быстрое подключение, минимум требований к сайту.
- Для мобильного трафика (а у ЦА2 он основной — Instagram/TikTok) deeplink в банковское приложение — это буквально два тапа, конверсия хорошая.

**Против СБП как единственного способа:**
- Часть покупателей не умеет или не хочет платить по QR — особенно на десктопе: нужно взять телефон, открыть банк, отсканировать. Часть просто уходит.
- Нет Apple Pay/Google Pay, нет сохранённых карт, нет оплаты «в один клик» → нет быстрого повторного заказа. А повторные заказы — ровно то, что нужно ЦА1 («заканчивается — беру»).
- Нет оплаты картами других стран и подарочными картами.
- Регулярные платежи по СБП технически существуют, но поддержаны провайдерами хуже карточных.
- Возврат по СБП работает, но инициируется только магазином и идёт на счёт плательщика — привычного «отмена по карте» пользователи не увидят, вырастет нагрузка на поддержку.
- Единственный способ оплаты = единственная точка отказа. Авария у НСПК или у банка — чекаут стоит.

**Рекомендация.** Стартовать с СБП — правильное решение экономически. Но выбрать провайдера так, чтобы карты включались настройкой, а не новым проектом:

1. Взять **агрегатор с фискализацией** (ЮKassa или Т-Касса) — СБП сразу, карты выключены.
2. Спроектировать **`PaymentGatewayInterface`** (`createPayment`, `getStatus`, `refund`, `handleWebhook`) и `ReceiptProviderInterface`. Провайдер — деталь реализации, а не архитектура.
3. Через 4–6 недель после запуска посмотреть в метрике долю брошенных оплат и решить по картам на данных.
4. На чекауте сразу заложить место под второй способ оплаты — чтобы потом не переверстывать.

### 1.4 Что нужно реализовать в интеграции оплаты (чеклист)

- [ ] Создание платежа с **ключом идемпотентности**; сумма считается на сервере, никогда не приходит с фронта
- [ ] Мобильные — deeplink в банковское приложение; десктоп — QR + кнопка «я оплатил» + поллинг статуса
- [ ] Страница ожидания оплаты с таймером **TTL QR** и корректным поведением при истечении
- [ ] Вебхук: проверка подписи, **идемпотентность по `external_id`**, ответ 200 только после сохранения, ретраи провайдера обработаны
- [ ] Статусная модель: `created → pending → succeeded | canceled | expired | refunded | partially_refunded`
- [ ] Снятие резерва склада при `expired`/`canceled`, фоновой задачей
- [ ] Полный и частичный возврат из админки + **возвратный чек**
- [ ] Чек 54-ФЗ: приход при оплате, предмет расчёта на каждую позицию, НДС, признак способа расчёта, доставка отдельной позицией
- [ ] Уведомления: e-mail + СМС/Telegram об оплате и об ошибке оплате
- [ ] Тестовый контур: пройден happy path, отказ, истечение, дубль вебхука, возврат
- [ ] Логи всех запросов/ответов с маскированием ПД, алерт при отсутствии вебхуков > N минут
- [ ] Сверка: ежедневный отчёт «заказы vs платежи vs чеки»

### 1.5 Юридическое и операционное вокруг платежей

| Тема | Что нужно | Комментарий |
|---|---|---|
| 54-ФЗ | Онлайн-касса + ОФД, чек покупателю в момент расчёта | Встроена у ЮKassa/Т-Кассы; при прямом СБП — своя облачная касса |
| Самозанятость | Если продавец — самозанятый, чек формируется в «Мой налог» | Самозанятый вправе продавать товары **собственного производства**; перепродажа — нет. У LIVSI производство своё, но налоговый режим надо подтвердить |
| Оферта | Публичная оферта на сайте + принятие галочкой с логированием | Пункт есть в футере макета |
| 152-ФЗ | Политика, согласие на обработку, уведомление РКН, хостинг в РФ | Уведомление подаётся **до** начала обработки |
| Возврат при дистанционной продаже | Покупатель вправе отказаться от товара в течение **7 дней после получения** — перечень невозвратных непродовольственных товаров к дистанционной торговле не применяется (ст. 26.1 ЗоЗПП) | Функционал возврата обязателен. Если не вложить в посылку памятку о порядке и сроках возврата, срок растягивается до 3 месяцев. Практическая защита — «товар был в употреблении». Подробно: `06-scope-v2.md`, § 2.2 |
| Маркировка «Честный знак» | Парфюмерия маркируется; по остальной косметике введение идёт поэтапно | **Проверить по конкретному ассортименту и датам.** Если попадает — коды маркировки обязаны попадать в чек, а отгрузка требует выбытия кодов. Это влияет и на кассу, и на склад |
| Документы соответствия | Декларации ЕАЭС / СГР — выкладывать в карточке | На этикетке в брендбуке есть знак ЕАС |

## Часть 2. Доставка

### 2.1 Ozon Доставка — как основной перевозчик

Речь про сервис доставки Ozon для сторонних интернет-магазинов (исторически «Ozon Rocket»). **Точное название продукта, тарифы, состав API и лимиты подтверждаются менеджером Ozon при заключении договора** — публичная документация закрыта.

**Плюсы**
- Огромная сеть ПВЗ и постаматов, в том числе в городах от 100 тыс. — это ровно география ЦА1.
- Узнаваемость: «заберу в Ozon» звучит понятно и снижает страх покупки в новом магазине.
- Тарифы для мелких лёгких посылок (флакон 100–300 мл) как правило дешевле курьерских служб.
- Есть API: создание отправления, этикетки, статусы, трекинг.
- Если заказчик уже продаёт на Ozon — единая логистика и знакомые процессы для склада.

**Минусы**
- **Одна служба = одна точка отказа.** Нет ПВЗ рядом — заказ не оформят.
- Курьерская доставка «до двери» покрыта хуже, чем ПВЗ, особенно в малых городах.
- Документация и песочница доступны только после договора → интеграцию нельзя оценить точно заранее.
- Строгие требования к упаковке, габаритам, весу и маркировке отправлений; нарушения — штрафы и отказы в приёмке.
- **Ограничения на жидкости, аэрозоли, спиртосодержащее.** Часть PRO-ассортимента (антисептики, кератолитики) может попасть под запрет или особые условия — проверить до запуска.
- Обратная логистика (невыкупы, возвраты) требует отдельного регламента на складе.
- Нет международной доставки; ограниченная гибкость по нестандартным габаритам (подарочные боксы из брендбука могут не пройти по размеру).
- Сроки перечисления выручки при наложенном платеже (если он поддержан) — по правилам Ozon, обычно с задержкой.

### 2.2 Альтернативы

| Служба | Плюсы | Минусы |
|---|---|---|
| **СДЭК** | Крупная сеть ПВЗ + курьер, зрелый и документированный API, готовые виджеты выбора ПВЗ, работает практически везде | Дороже Ozon на мелких посылках; качество ПВЗ по франшизе плавает |
| **Почта России** | 100 % охват страны, включая села; дешёвая пересылка мелких посылок; API есть | Долго; качество сервиса неровное; ниже доверие покупателей |
| **Яндекс Доставка** | Курьер за 1–2 часа и в день заказа, отличный API, хорошо в миллионниках (ЦА2) | Дороже; ПВЗ-сеть скромнее; межгород слабее |
| **Boxberry** | Хорошие ПВЗ в европейской части, адекватные тарифы | Сеть сжалась, покрытие неравномерное |
| **5Post (X5)** | Пункты выдачи в «Пятёрочке»/«Перекрёстке» — удобно и очень плотно | Жёсткие лимиты по габаритам/весу; только ПВЗ |
| **Агрегатор (Apiship, Shiptor)** | **Одна интеграция → десятки служб**, единый расчёт «покажи все варианты», виджет карты со всеми ПВЗ, лёгкая замена перевозчика | Наценка агрегатора; ещё один посредник в цепочке поддержки |
| Самовывоз (Ставрополь, производство) | Бесплатно, лояльность локальных клиентов | Нужны график и ответственный на месте |

### 2.3 Рекомендация по доставке

1. **На старте — Ozon как основной способ** (это решение заказчика и оно разумное: цена + сеть ПВЗ) **плюс самовывоз в Ставрополе.**
2. **Спроектировать `DeliveryProviderInterface`** (`calculate`, `pickupPoints`, `createShipment`, `label`, `track`, `cancel`) и завести Ozon как первую реализацию. Добавить СДЭК позже — это дни, а не недели.
3. **Всерьёз рассмотреть агрегатор (Apiship) вместо прямой интеграции**, если заказчик готов к небольшой наценке: одна интеграция закрывает и Ozon, и СДЭК, и Почту, и даёт готовый виджет карты ПВЗ. Для магазина такого размера это обычно выгоднее по совокупной стоимости владения, чем две-три прямые интеграции.
4. **Обязательный фолбэк — «ручной режим»**: если API перевозчика недоступен, заказ всё равно оформляется, стоимость доставки менеджер уточняет и досогласовывает. Без этого падение Ozon = остановка продаж.
5. **Заполнить вес и габариты каждого варианта товара** до этапа 6 — без этого расчёт доставки невозможен, и это самая частая причина срыва сроков на этом этапе.

### 2.4 Чеклист интеграции доставки

- [ ] Синхронизация справочника ПВЗ/постаматов (координаты, адрес, часы, лимиты, фото) — кроном, с кэшем
- [ ] Виджет выбора ПВЗ на карте (Яндекс.Карты) + поиск по адресу + список
- [ ] Расчёт стоимости и срока: по городу, весу, габаритам, объявленной стоимости
- [ ] Правило «бесплатная доставка от 3 000 ₽» (из макета) — уточнить порог и **кто платит разницу** (это прямой вычет из маржи)
- [ ] Создание отправления при оплате, номер и трек в заказ
- [ ] Печать этикеток/ШК, реестр отгрузки для склада
- [ ] Трекинг: вебхуки или поллинг, история статусов, письма покупателю на ключевых статусах
- [ ] Обработка невыкупа/возврата: статус, возврат денег, возврат товара на склад
- [ ] Ограничения ассортимента: пометка товаров, которые нельзя отправлять данной службой
- [ ] Фолбэк при недоступности API + алерты

## Часть 3. Итоговая рекомендация в двух строках

**Оплата:** СБП через агрегатор с встроенной фискализацией (ЮKassa / Т-Касса), карты — выключенным тумблером; всё за `PaymentGatewayInterface`. Решение о картах принять на данных через месяц после запуска.

**Доставка:** Ozon + самовывоз на старте, за `DeliveryProviderInterface`, с обязательным ручным фолбэком; агрегатор (Apiship) — как более дешёвый в владении вариант, если заказчик не против наценки.

## 7. ЮKassa — реализовано 07.09.2026

Провайдер выбран заказчиком. Это тот вариант, который был заложен запасным (§ 6 и `06-scope-v2.md` § 2.6): вопрос о Точке больше не блокирует оплату.

### 7.1 Оплате был нужен заказ

Платить было не за что: в проекте есть корзина, но нет заказов. Поэтому увеличение включает всю цепочку — `orders`, `order_items`, `payments`, оформление, возврат покупателя, вебхук.

**Позиции заказа — снимок.** Артикул, название, цена и ставка НДС сохраняются на момент покупки. Ссылки на вариант мало: цена меняется, вариант выключают, а в заказе и в чеке должно навсегда остаться то, что человек купил. На это есть тест — он переименовывает товар и меняет цену после оформления.

### 7.2 Чек 54-ФЗ

Две вещи, из-за которых чек собирается отдельным классом, а не парой строк в шлюзе.

**Сумма позиций обязана совпасть с суммой платежа.** Скидка за подарок распределяется по позициям пропорционально, остаток от деления раздаётся по копейке самым крупным позициям. Округление каждой доли по отдельности этого не гарантирует, а чек, который не сходится на копейку, провайдер отклонит.

**В чеке указывается цена за единицу, а не сумма строки.** Если после скидки сумма строки не делится на количество нацело, строка разбивается на две: несколько единиц по одной цене и одна по другой. Иначе сойтись невозможно в принципе.

Сумма платежа берётся из чека, а не из заказа: два независимых подсчёта рано или поздно разойдутся.

**Ставка задаётся свободно, а её код — настройкой.** В чек уходит не процент, а код ставки, и назначает его ФНС. Жёсткий список 0/10/20 устарел в тот момент, когда с 1 января 2026 года основную ставку подняли до 22 % (ст. 164 НК РФ в редакции ФЗ от 28.11.2025 № 425-ФЗ). Сейчас действуют 22 %, 10 %, 0 %, а для УСН — 5 % и 7 % по порогам дохода.

Поэтому соответствие «ставка → код» лежит в настройках и правится заказчиком по документации провайдера. Коды по умолчанию взяты оттуда же:

| Ставка | Код в чеке |
|---|---|
| без НДС | 1 |
| 0 % | 2 |
| 10 % | 3 |
| 20 % | 4 |
| 5 % (УСН) | 7 |
| 7 % (УСН) | 8 |
| 22 % | 11 |

Порядок кодов не повторяет порядок ставок: 5 % — это код 7, а 7 % — код 8. Перепутать их легко, а обнаружится это только при сверке с налоговой, поэтому таблица закреплена тестом.

Расчётных ставок (10/110, 20/120, 5/105, 7/107, 22/122 — коды 5, 6, 9, 10, 12) в таблице нет: они не выражаются процентом и применяются к авансам и агентским операциям, которых у розничного магазина не бывает.

Если закон введёт ещё одну ставку, заказчик добавит её в ту же таблицу, не дожидаясь выката. Строка без кода не работает намеренно: платёж по такой ставке не создаётся, а сообщение прямо называет ставку. Пустой код при этом не превращается в ноль — ноль это код ставки 0 %, и чек ушёл бы без налога. На это есть отдельный тест.

**Пустая ставка НДС не подменяется нулём.** Ноль — это осознанная ставка 0 %, а пусто означает «не выяснили». Платёж в этом случае не создаётся, и человек видит понятное сообщение. Отправить угаданную ставку хуже: чек придётся корректировать, а расхождение всплывёт при проверке. В настройках появились «ставка по умолчанию» и «продавец не платит НДС» — второй случай даёт признак «без НДС» на весь чек.

### 7.3 Что сделано против типичных ошибок

| Риск | Что сделано |
|---|---|
| Сетевой сбой создаёт второй платёж и второе списание | Ключ идемпотентности в заголовке, повтор запроса безопасен |
| Вебхук объявляет любой заказ оплаченным | Проверка адреса отправителя по списку сетей провайдера **и** перепроверка статуса запросом к API — телу уведомления не верим |
| Повторное уведомление списывает товар дважды | Все переходы идемпотентны; провайдер доставляет «хотя бы один раз», дубли будут обязательно |
| Двое оплачивают последнюю единицу | Резерв квоты ставится при создании заказа, а не после оплаты |
| Провайдер отказал — товар завис недоступным | Резерв снимается, корзина не очищается, человек возвращается к своим товарам |
| Покупатель вернулся раньше вебхука и видит «ждём оплату» | Страница заказа сама спрашивает статус у API |
| Отмена по второй попытке отменяет оплаченный заказ | Оплаченный заказ вебхуком не отменяется; пока жива другая попытка, заказ остаётся в ожидании |

Гостю кабинет не положен, поэтому заказ открывается по номеру и неугадываемому токену. Токен сравнивается постоянным по времени сравнением: обычное сравнение строк подсказывает, сколько символов совпало.

### 7.4 Чего в этом увеличении нет

- **Доставки.** Поля в заказе заведены, но расчёт стоимости, выбор ПВЗ и передача в Ozon — отдельный блок. Пока на странице честно написано, что доставка считается отдельно и оплачивается при получении.
- **Писем.** Заказ и чек уходят покупателю от провайдера; собственных писем о заказе ещё нет — это блок транзакционных писем.
- **Возвратов.** Возврат денег через API — отдельная задача, связанная с заявкой на возврат.
- **Отмены по таймауту.** Резерв снимается при отмене платежа, но заказ, брошенный на платёжной странице, освободит квоту только когда провайдер отменит платёж по своему таймауту. Отдельная задача — снимать резерв по расписанию.

### 7.5 Проверено

29 тестов на цепочку, всего в проекте 327. Ответы провайдера подставляются: настоящие тестовые платежи требуют ключей из личного кабинета заказчика.

Проверены в том числе: сумма чека совпадает с заказом до копейки; строка, не делящаяся нацело, разбивается на две; распределение скидки не теряет копеек на трёх разных наборах; повторное уведомление не списывает товар дважды; уведомление с постороннего адреса отклоняется; заказ не становится оплаченным, если в теле уведомления «оплачено», а API отвечает «ожидает».

### 7.6 Что нужно от заказчика для настоящих тестовых платежей

1. В личном кабинете ЮKassa создать **тестовый магазин** и взять `shopId` и секретный ключ (он начинается с `test_`).
2. Положить их в окружение: `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`.
3. Указать в настройках сайта ставку НДС. Коды для чека уже проставлены, менять их не нужно. У этого продавца УСН, поэтому ставка скорее всего 5 % или 7 % — зависит от годового дохода; подтвердить её должен бухгалтер письмом (§ 2.3 в `06-scope-v2.md`).
4. Прописать в кабинете адрес для уведомлений: `/webhooks/yookassa`. Без него статус будет обновляться только когда покупатель вернётся на сайт.

Проверить подключение: `php artisan payments:check` — команда не создаёт платежей, только спрашивает у провайдера, принимает ли он ключи, и печатает адрес для уведомлений.

### 7.7a Корневые сертификаты на машине разработчика

Первая попытка оплаты упёрлась не в код:

```
cURL error 60: SSL certificate problem: unable to get local issuer certificate
```

В поставке PHP для Windows нет списка корневых сертификатов, а `curl.cainfo` и `openssl.cafile` в `php.ini` пустые. Проверить подпись сервера нечем, поэтому PHP отвергает **любое** HTTPS-соединение — не только к ЮKassa. Дальше это же сломало бы отправку почты и любой другой внешний вызов.

Лечится в `php.ini`, а не в проекте: набор сертификатов нужен всему PHP, а не одному нашему клиенту. Прописать путь к файлу `cacert.pem` (curl.se/ca/cacert.pem) или к `ca-bundle.crt`, который уже лежит в составе Git для Windows:

```ini
curl.cainfo = "C:\путь\к\cacert.pem"
openssl.cafile = "C:\путь\к\cacert.pem"
```

Проверять `php artisan payments:check` — команда теперь ловит обрыв соединения отдельно от ошибок API и печатает эту инструкцию.

Отключать проверку сертификата (`verify => false`) нельзя ни при каких условиях: это ровно тот случай, ради которого проверка существует — платёжный трафик с ключами магазина.

**Отдельным следствием этой ошибки нашлась утечка.** Текст исключения уходил покупателю на экран как есть, и он видел `api.yookassa.ru` со ссылкой на документацию curl. Теперь при любом сбое создания платежа покупателю показывается одно сообщение, а причина пишется в лог; на экран она попадает только при включённом `APP_DEBUG`. Раньше так же утекало и «не задана ставка НДС» — сообщение для администратора, а не для покупателя. Закреплено тремя тестами.

### 7.7 Нужен ли публичный адрес

Короткий ответ: для **вебхука** — да, для **проверки оплаты локально** — нет.

**Почему локально всё-таки работает.** Страница заказа сама спрашивает у API статус платежа, когда покупатель возвращается с платёжной страницы. Это сделано не ради локальной разработки, а потому что возврат покупателя почти всегда опережает вебхук: иначе человек, только что заплативший, видел бы «ждём оплату». Побочный эффект — весь путь «корзина → оформление → оплата → оплаченный заказ → списание квоты» проверяется на `localhost` без единого входящего запроса снаружи.

**Что теряется без вебхука.** Заказы, где покупатель не вернулся: закрыл вкладку, оплатил по СБП с телефона, потерял связь. Такой заказ останется в «ждёт оплаты», пока кто-нибудь не откроет его страницу. На боевом контуре это недопустимо — деньги списаны, а заказ не виден менеджеру.

**Как проверить вебхук локально.** Поднять туннель (`ngrok http 8000`, `cloudflared tunnel`, `localhost.run`), указать его адрес в кабинете ЮKassa и дописать в окружение:

```
TRUSTED_PROXIES=*
YOOKASSA_WEBHOOK_IPS=185.71.76.0/27,185.71.77.0/25,...,<адрес туннеля>
```

Первое нужно потому, что через туннель запрос приходит от прокси и настоящий адрес отправителя лежит в заголовке — без этого проверка видит `127.0.0.1` и отклоняет всё. `TRUSTED_PROXIES=*` допустим только локально: на боевом контуре там перечисляются адреса балансировщика, иначе адрес отправителя можно подделать заголовком.

**Почему расширять список сетей не опасно.** Проверка адреса — второй рубеж, а не единственный. Статус платежа всё равно берётся запросом к API по Basic-аутентификации, а телу уведомления мы не верим. Поэтому даже с полностью пустым списком подделать оплату нельзя — на это есть отдельный тест: поддельное уведомление со статусом «оплачено» не делает заказ оплаченным, потому что API отвечает «ожидает».

**Что нужно на боевом контуре.** HTTPS-адрес (у ЮKassa требование к уведомлениям), прописанный в кабинете, и `TRUSTED_PROXIES` с адресами балансировщика. Это часть задачи со staging на Timeweb Cloud.
